Frontend Handoff: Search and Filter Backend Changes
Date: 2026-03-17
Project: SeniorProject-Backend

Overview
- List endpoints now support consistent pagination response shape:
  - data: array
  - meta: { total, page, limit, totalPages }
- Search/filter query support has been expanded across all major list APIs.
- New generic keyword query param is: q
- Text matching behavior in repositories is now mostly case-insensitive contains.

Important Notes For Frontend
- Continue sending page and limit from the UI.
- Send q for global keyword search in list pages.
- Keep sending specific filter fields as needed (role, status, locationId, etc.).
- Responses are server-paginated; do not slice list data again on the client.

Behavior Updates Worth Calling Out
- /locations deleted filter now correctly maps to deleteStatus in repository logic.
- Team and UserCreateStatus list APIs now support full options object (including q) instead of deleted-only filtering.
- Several list endpoints changed exact string equality filters to contains + case-insensitive matching.
- Some endpoints also attempt numeric matching from q when q can represent IDs.

Frontend Integration Checklist
- Add q input on list pages where global search is desired.
- Keep existing column filters; they now combine with q.
- Keep table pagination fully server-driven using meta.total and requested page/limit.
- Validate empty-state UX when q/filter returns zero rows.
- Validate that filter chips/query-state map exactly to these param names.
